# Agent Note：首绘后启动 I/O 调度

状态：已实现

[English](2026-08-31-post-paint-startup-io-scheduling.md) | 中文

## 问题

Web Runtime 在连接就绪后立即启动当前 Session 历史与 Workspace 基线。此前，本地插件会在同一次首屏渲染期间同时发起布局恢复、Explorer 标记校验和审核目标校准。这些相互独立的磁盘读取与文件系统检查会和显示当前对话、Explorer 根目录所必需的内容争抢资源。

## 决策

Client Runtime 提供 `ctx.startupTasks`，作为在两个动画帧后开放的单一串行队列。后台页面收不到动画帧时，由 200 ms 定时器开放队列。每个任务相互隔离：失败只会拒绝自身的完成 Promise，队列会继续执行。调用方拥有的 `AbortSignal` 会跳过因 Session 或 Workspace 变化而过期的任务；功能原有的 generation 或 revision token 仍负责阻止已经开始的任务发布迟到数据。Runtime 销毁时，排队但尚未开始的任务会直接完成而不执行。

当前 Session 历史、Workspace/Session 列表、Explorer 根目录读取和持久化审核快照仍保留在关键路径。Better Sidebar 延后 Host 布局恢复与 Emoji 标记校准。Explorer 可见性被拆为两步：轻量持久化意图快照先约束根目录渲染，避免隐藏条目闪现；文件系统存在性校准稍后执行。File Edit 先显示持久化待审核账本，只把逐目标校准提交到延后队列。

## 考虑过的替代方案

**每个插件分别使用定时器。** 未采用，因为独立定时器无法跨插件串行，也没有共同的销毁所有者，多个磁盘密集任务仍可能同时开始。

**延后完整的 Explorer 可见性恢复。** 未采用，因为被标记隐藏的条目会在延后状态到达前短暂显示。因此，持久化隐藏意图属于关键数据，只有文件系统校准进入延后队列。

**把审核快照和校准一起延后。** 未采用，因为待审核内容是用户可见的权威状态，重启后必须立即出现；只有目标校验属于首绘后任务。

## 结果

首屏关键读取不再与每个本地恢复任务同时启动，首绘后的磁盘任务也不会并发散开。该队列不会削弱持久化或审核权威，只改变调度时机：待审核内容仍先于校准显示，隐藏意图仍在根目录行渲染前生效，所有迟到响应仍由其所属功能保护。

## 验证

调度器测试覆盖双帧门禁、严格串行、取消、失败隔离和销毁。Better Sidebar 测试覆盖延后布局恢复、迟到响应拒绝、文件系统校准前的持久化可见性，以及完整既有 Explorer/Preview 套件。File Edit 在保留完整账本与删除套件的同时，通过 Client 源码契约固定“快照优先、校准延后”的顺序。
