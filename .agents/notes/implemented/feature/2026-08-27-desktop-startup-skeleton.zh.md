# Agent Note: 桌面启动页暗示工作区三大区域

Status: implemented

[English](2026-08-27-desktop-startup-skeleton.md) | 中文

## 问题

桌面壳需要在内置 runtime 与本地回环 Web 后端就绪前显示一份本地文档。居中的状态卡片让等待过程看起来像独立弹窗，暴露出大片空白区域，并在三栏 Harness 工作区替换它时产生突兀跳变。Renderer 加载前，桌面壳也无法获得 Harness 的外观偏好，因此当软件主题与操作系统主题不同时会短暂闪现错误背景。

## 决策

Electron Main 负责一份无外部依赖的启动文档，只用三个中性大色块代表会话列表、Explorer 和对话主区。它有意省略控件与内容占位，只暗示整体板块结构。低对比度 shimmer 表达加载进度并遵守减少动态效果偏好，底部的小型实时状态区域保留完整启动提示。文档使用亮暗 CSS 变量，BrowserWindow 背景采用同一套颜色。

preload 的外观消息继续作为 Renderer 向 Main 传递主题的唯一输入。Main 校验其中的 `light` 或 `dark` 值并原子写入 `appearance-state.json`；下次启动会在创建 BrowserWindow 前应用该值，文件缺失或无效时则跟随操作系统。后端确认就绪后，Main 先淡出骨架，再让同一窗口导航到本地回环地址。启动失败仍使用诊断状态文档和原生错误对话框，因为失败态需要呈现可操作信息，而不是无限期占位。

## 考虑过的替代方案

**重新设计居中卡片。** 这能改善排版，但仍会保留类似弹窗的跳转和大片空白窗口，使启动过程继续与产品正式界面割裂。

**加载带模拟数据的完整 React 应用。** 这样能精确复现界面，但会把 Web runtime 和插件依赖图引入一个正因这些依赖尚未就绪才存在的阶段。

**使用第二个透明 splash 窗口实现跨窗口溶解。** 它可以覆盖 Web 首帧，但会为短暂的本地过渡增加窗口生命周期、焦点、无障碍和多显示器复杂度。同窗口淡出能够保持启动所有权和失败恢复简单。

## 后果

首个可见画面只暗示正式应用的三个主要区域和主题体系，不暗示具体控件位置，后续启动也不会再闪现相反主题。占位页不共享正式组件，只在 `startup-document.mjs` 中近似主要区域比例。单元测试固定三个区域、不出现详细 UI 占位、主题和减少动态效果规则、状态文案、旧卡片移除以及经过校验的外观持久化。
